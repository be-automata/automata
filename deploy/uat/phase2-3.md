## Notes

**Why N = 2 is not the steady state on this box (and #371 says so).** With the box's own
numbers — run commit = `WORKER_RUN_MEMORY_MAX` = 5000M ≈ 4.9 GiB, idle `Committed_AS` ≈ 2.4 GiB,
`CommitLimit` ≈ 11.8 GiB × 0.9 ≈ 10.6 GiB — one admitted run plus a second arriving is
2.4 + 4.9 + 4.9 ≈ 12.2 GiB > 10.6 GiB: the commit arm defers every second concurrent run, and if
the first outlasts the 366 s budget the second fails final. Shrinking the reservation by the
run's anonymous memory does not change the sum (it moves bytes from `reserved` into
`Committed_AS`). So #371 at N = 2 on a CX33 turns "waits at the engine" into "dispatched,
deferred, fails after ≈ 6 min" — the check working as specified, not failing. The #205 N = 2
drill (`phase2-2.md`) was therefore captured on the pre-#371 code, and the box returns to
`WORKER_BOX_SLOTS=1` BEFORE the restart that brings #371 up. Raising N here needs a lower
`WORKER_RUN_MEMORY_MAX` or more memory, and the arithmetic above is the sizing rule.

**Drill log (all UTC, 2026-10-19):** deploy of main `66f66dd4` at 13:35:47 (boot line 13:35:54); rows 2–3 with hog `4 GiB` 13:37:06–13:37:20 and run `ae5e66e6` (2 deferrals, admitted on attempt 2, completed 13:37:53); rows 4–6 with the hog held 13:38:34–13:45:00 and runs D `1bb42c31` (8 deferrals → final failure 13:44:57) and E `398ef63e` (queued → admitted 13:45:54 → completed 13:46:23). Memory-hog: `/root/memhog.py <GiB>` (anonymous `mmap`, every page touched, outside the worker cgroup; `stress-ng` is not installed). Sampler TSV kept on the box.

**Operational finding — a deferred run is invisible to cgroup-based idle checks, and it holds the SDK drain.** While a run waits in process it holds no run cgroup, no box lock and no run dir: the restart recipes (this session's `deploy-box.sh` and evidently another session's) decide "nothing in flight" from exactly those signals, so a concurrent deploy issued `systemctl restart` at 13:39:51 with D deferring. The SDK paused the worker and drained; the drain waited on D for 5 minutes (a deferring run can hold it for the whole budget, up to 12 min), D failed on schedule at 13:44:57, the drain completed, and the engine redelivered D to the next worker process (attempt 0) — the headroom failure itself was never retried by the engine, but a failure that ends a drain IS re-executed, an exactly-once hole filed as a follow-up. Before any worker restart: check `systemctl list-jobs` (a pending stop job means a drain is in progress), the engine worker row (paused), and the journal for a `Task run starting` without a matching `completed`/`failed` in the last 30 minutes or a `box.headroom_deferred_wait` in the last 12; expect a restart issued during a deferral to block until that run is admitted-and-finished or fails final. `deploy/README.md` says so now; a worker-side in-flight gauge for the restart recipe belongs to #373 (observability).
