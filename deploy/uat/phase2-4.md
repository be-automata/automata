## Decisions recorded (ticket items 5 and 6)

**Production tuple — concurrency 3 (ticket option (a), the epic's DoD; operator decision
2026-10-19).** Measured on the box (sampler `/var/tmp/automata-mem-samples.tsv`, 36 runs; journal,
7 d): review-lane peak p95 0.15 GiB; task-lane median 0.26 GiB but max 4.49 GiB sampled and 6
OOM-kill / `memoryStarvation` lines at the 5000M ceiling. So the ceiling cannot drop below 5000M
without killing task runs — option (b) (cx33, lower ceiling) is out. **Chosen: resize to cx43
(16 GB RAM, 8 vCPU; the epic's authorized RAM-trigger move — the OOM evidence fires it) and run
`WORKER_BOX_SLOTS=3 WORKER_GLOBAL_MAX_RUNS=3 WORKER_PER_ORG_MAX_RUNS=2 WORKER_RUN_MEMORY_MAX=5000M`
with `vm.overcommit_ratio=80`.** The arithmetic that makes three 5000M runs admissible: at the
kernel default `overcommit_ratio` 50, cx43's `CommitLimit` = 8 GB swap + 0.5 × 16 GB = 16 GB, and
the #371 commit arm (0.9 × 16 = 14.4 GiB) admits two runs beside the ≈ 2.6 GiB base (12.4 GiB) but
defers the third; the #372 boot check uses the SAME budget and refuses the tuple outright. In
real units (5000M = 5.24 GB; swap 8 388 604 kB = 8.59 GB; cx43 `MemTotal` ESTIMATED at
16 258 000 kB = 16.6 GB by scaling the cx33's 7 937 228 kB — the same figure the unit fixture
`CX43_R80` models; row 2 replaces every number here with the measured `/proc/meminfo` after the
resize and the sysctl): at `overcommit_ratio` 80, `CommitLimit` ≈ 8.59 + 13.3 = 21.9 GB and the
budget is 0.9 × 21.9 = 19.7 GB. The boot check passes (3 × 5.24 + 2.15 base = 17.9 GB < 19.7 GB,
a 1.8 GB margin — a run commit above ≈ 5.8 GB would refuse). At run time the commit arm admits
the third run while `Committed_AS` + 3 × 5.24 ≤ 19.7 GB, i.e. while the live base is ≤ 4.0 GB:
0.5 GB of margin at the observed idle high end (3.5 GB), 1.3 GB at the low end (2.7 GB). If the
MEASURED budget leaves no margin at the observed base, the plan (not a contingency) is
`overcommit_ratio` 90 before the tuple is applied; a deferral that appears later means the base
grew and the same move applies. 3 × 5.24 = 15.7 GB stays under the 16.6 GB of RAM so the
`warnIfSlotsExceedMemory` warning stays quiet (swap absorbs a peak). `vm.overcommit_memory` stays 0
(heuristic): `CommitLimit` is the headroom check's budget signal, not a kernel-enforced cap.
Code defaults stay 1/1/1 so an unprovisioned box still boots. Per-org 2 < global 3 bounds one org to 2 of the 3 slots PER WORKFLOW VARIANT (both keys are per variant — definition.ts); one org with a review on `agent-run-newest` and task runs on `agent-run` can still hold all 3 worker slots, so cross-variant per-org fairness is NOT guaranteed by these caps — only GROUP_ROUND_ROBIN's ordering within a variant is. A worker-side per-org count at admission would close that; tracked as a follow-up under #373's per-client share trigger, not this ticket. The sysctl lands
with the resize (`/etc/sysctl.d/90-automata-overcommit.conf`) and is recorded in row 2.

**Supersede waste — accept and measure.** `newest-wins` keeps a verdict current with the
latest push; moving high-churn repos to `complete-run-discard` would trade compute for stale
verdicts. The worker writes `box.supersede_waste {runId, threadId, lane, policy, executionMs}` to the ENGINE task log (`ctx.log`, not the journal) on every superseded terminal it posts, measured from the task fn's start (admission and headroom waits included — the same window as the engine's `finishedAt − startedAt`); the 7-day fraction is #373's trigger, revisited above ~20 %.

(17:27, 17:38, 17:40 UTC) failed with Hetzner `resource_unavailable`; `cx53` likewise, and `cpx41` "can

`payload seal: 1 key(s) usable` line re-verified after every power-on). Operator decision 18:48 UTC:
**cpx42** (8 vCPU AMD, 16 GB, available in fsn1, ~€82/month vs cx43's €18.49). The memory arithmetic of
the Decisions section is unchanged; the measured figures replace the estimates (`MemTotal` 15 987 540 kB
vs the 16 258 000 kB estimate; `CommitLimit` 21 178 636 kB vs ≈ 21.9 GB). The server can be moved back
to cx43 with `--keep-disk` when capacity returns.

**Provisioning gap found and fixed.** §6 of `AGENT-UID-PROVISIONING.md` re-renders the EGRESS nft set
for the new slot uid but did not say to re-render the #367 LOOPBACK table (§7) too: the worker's
`ExecStartPre` loader refused the start twice (`[nft-loopback-load] FAIL: skuid set {999 2001} is not the
set the egress fence covers {999 2001 2002}`, 18:53:35 and 18:54:21 UTC — fail-closed as designed) until
`loopback-nft.conf` was re-rendered with `999, 2001, 2002` (`tables 7 -> 7`, 18:54:27). §6 now carries
the step (3b).

**Verdicts blocked by the credential, not by the plane.** All three drill reviews posted "Automata has no
verdict" notices: each daemon ACKed the 11 884-byte prompt and the thread completed 8–10 s later. The

disabled Claude subscription access for Claude Code · Use an Anthropic API key instead, or ask your admin
to enable access"_ (`is_error: true`, 394 ms, cost 0) — the Anthropic organisation that owns the delivered
owner credential has turned subscription use off. Every review run that delivers that credential fails
the same way until an admin re-enables it or the platform stops delivering it. **Fallback tried and reverted (peer session):** at 19:05:15 UTC the vendor org's `claudeCode`
setup-token row in `agent_provider_credentials` (id `f148720d…`) was set `is_active = false` so reviews
would bill the built-in key. That path failed too ("Credit balance is too low", credential source
built-in credits, thread `9f481987`), so the row was restored to `is_active = true` at 19:07:21 UTC.
Both credential paths are dead as of this record. A review run at about 21:45 UTC (PR #401) again
logged `delivered user credential` and posted a no-verdict notice. The fix is the operator's:

key. The concurrency evidence in rows 2–3 is
unaffected: it is the worker/engine/box path up to and including the daemon hand-off and teardown.
