## Why this design (composable executor)

`runAgentInner` (`packages/worker/src/agent-run/workflow.ts:1219-1992`) is one 770-line function that owns the box path end to end: slot and admission (`:1275-1432`), host clone (`:1434`), credential materialisation (`:1563`), the local egress proxy (`:1604-1636`), local git and gh brokers (`:1645-1690`), the container daemon (`:1697-1724`), the poll (`:1832`) and an ordered teardown (`:1858-1985`). Almost nothing of that applies to a cell. The cell has its own egress sidecar, its own vault, the www-hosted broker, and no host checkout or mounts.

So the cell path is a **second executor behind one seam**, chosen once per run. It is not a set of `if (cell)` branches inside `runAgentInner`:

- `RunExecutor` (new) is the seam. `boxExecutor` wraps today's `runAgentInner` byte for byte. `cellExecutor` is the new module.
- The only parts shared with the box path are the ones that are the same by definition. They are lifted out without changes:
  - **Admission:** the slot and headroom loop, moved into `run-admission.ts` (`admitRunSlot`, with the admission state it owns, Decision 2). A cell still spends this box's memory and CPU.
  - **The outer wrapper:** `runAgentResolved`, with the stale skip, the abnormal-end state, `postSuperseded` and the `stopped` → `user-cancelled` post.
  - **The poll:** `pollUntilTerminal`.
- Every dependency of the cell executor is injected: the www calls, the provider factory, the clock, sleep and the logger. It runs in tests against fakes and in production against `createOpenSandboxCellProvider`. Swapping in #635's Gondolin later is a different `ICellProvider`, not a new branch.
- **Adopt over build:**
  - the OpenSandbox adapter (`@terragon/sandbox/opensandbox-cell`);
  - upstream execd's own `POST /files/upload` for writing files into the cell (`components/execd/pkg/web/router.go:74`, `release-1.2.1`), instead of a home-grown argv channel;
  - the cell image's `cell-entry.sh` and `cell-send.sh` (PR-F);
  - the existing www-client poll, its auth-confirm rule and the abnormal-end module.
- **Built here:** the executor, the teardown sequencer and the cell www client. They exist because no upstream owns our revoke-before-teardown contract.

## Decisions

1. **Executor seam.** `selectRunExecutor(input, {box, cell, loadCellConfig})`. Both executors are **injected**, so `run-executor.ts` imports no cell module and phase 5 wires the box alone (with `cell` = a refusing stub until phase 6b):

   - no marker → `boxExecutor`, which is exactly `runAgentInner`;
   - marker + `cellConfig.kind === "on"` + lane `task` + no `selfHeal` + no `reviewAgent` → `cellExecutor`;
   - marker + anything else → throw `CellRunRefusedError("cells_unconfigured" | "cell_lane_refused")`. This is a `NonRetryableError`, raised before admission, so nothing is held.

   The marker is the only switch. The worker never runs an unmarked run in a cell.

   **Owner decision (2026-11-17):** with the flag on, the marker is set. If the worker's `WORKER_OPENSANDBOX_*` env is unset or invalid, the marked run **fails closed with `cells_unconfigured`**. It never falls back to the box. With the flag off, the run takes the old box path byte for byte (T-FLAG-OFF). `loadCellConfig` is read **only for a marked run** (inside `selectRunExecutor`, after the marker check), so an unmarked run never touches the key file.

2. **Admission is shared, extracted as a move, not verbatim.** The loop at `workflow.ts:1275-1432` uses `workflow.ts` module state. `run-admission.ts` therefore **owns** all of it:

   - `admissionGate`, `admissionGateFor`, `getAdmissionController`, `headroomBootWarning`, `headroomBootLine`, `sleepAbortable` and `admissionSleep`, with the `_setAdmissionSleepForTests` / `_setAdmissionControllerForTests` seams (`workflow.ts:418-511`);
   - the local `staleSkip` (`:1189`), and the `RunCtx` type (`:403`).

   `workflow.ts` imports them from `run-admission.ts` and **re-exports** the names that outside modules import from `./workflow`: `workflow-cleanup.test.ts:427` and `:2563-2617` (the two seams), and `hello/worker.ts:37` (`headroomBootLine`, `headroomBootWarning`). `run-admission.ts` imports nothing from `workflow.ts`, so there is no import cycle. The loop itself moves `admitRunSlot(...)` → `{kind: "admitted", boxLock, config, reservation} | {kind: "skipped", output}`. `runAgentInner` calls it in the same place.

   - **The release-on-throw split:** today one `try` (`workflow.ts:1288`) covers both the admission loop **and** the clone (`provisionWorkdir`, `:1434`), and its `catch` (`:1443-1446`) releases the reservation and the slot. After the move there are two equivalent guards:
     - `admitRunSlot` has its own `try/catch` around the loop and the post-deferral stale re-check. It releases what it holds and rethrows. The skip branch's inline releases (`:1404-1408`) move with it unchanged.
     - `runAgentInner` keeps a `try/catch` around `provisionWorkdir` alone, with the same two releases.
     - Net behaviour: the same releases on the same throws, in the same order. The cell executor wraps its plan fetch in the same kind of guard (Contract 7, step 2).
   - The diff in `runAgentInner` is that call, the narrowed `try`, and the deletion of the moved lines, with no reordering. The cell keeps its full `runCommitBytes` reservation for its whole life, because its memory lives in another daemon's cgroup and `observe` is not wired. That is conservative.

3. **Files go in through `copyIn`, adopting upstream execd's upload.**
   - `ICellProvider.copyIn(cellId, path, bytes, opts: {mode: number; owner: string; group: string})`, implemented in the adapter as `POST /proxy/<execd>/files/upload`. The wire format is in Contract 9. It is capped (16 MiB), `retry: "undelivered"`, and never logs the body.
   - **Why:** execd's command path logs the exec command (`packages/types/src/cell.ts:165-170`; `gate-log-b.md:15`, "execd's command log holds that encoding by design"). The message carries the prompt (H2-sensitive, `www-client.ts:96-101`), and `CELL_SEND_MAX_BYTES` would fail any large prompt. For an upload, execd's request log records the method and URL only (`logMiddleware`, `router.go:289-293`), and the path rides in the multipart body, so the prompt stays out of execd's logs.
   - **Rejected:** base64 in argv (the prompt lands in the command log, and the 128 KiB cap applies); splitting over several execs (the same log); a new image script (an image rebuild for no gain).
   - **What runs:** `exec(["/bin/bash", "-c", CELL_WRITE_MESSAGE_SH, "cell-write", "<path>"])`, a fixed script string that runs `/usr/local/bin/node $CELL_DAEMON_BUNDLE --write --socket-path $CELL_DAEMON_SOCKET --timeout 10000 < "$1" && rm -f "$1"`. Only the path is in argv. The file is mode 0600 under `~/.automata-run/` and removed after the write.
   - **The staging window:** upstream creates the file with `0777 &^ umask` and chmods it to the requested mode only after the write (`filesystem_upload.go:237`, `:442`). So the message is written **only into `CELL_MESSAGE_DIR`**, which `cell-entry.sh` creates 0700 (its umask-scoped `mkdir`, `spec-f.md:229-231`). No other uid can traverse that directory during the window, and the cell has one uid anyway. `copyIn` is not used for anything sensitive outside a 0700 directory.
4. **The provider is built per run, after the plan** (H12), from `cellConfig` + `cellEntrypoint(plan.tags.deployment)` + `CELL_SELF_CHECK_ARGV`. `deps.fetch` is the global fetch. `deps.logger` is a prefixed run logger that drops field values, the way `cell-control.ts:73-86` does.
5. **Teardown goes step by step, not through `teardown()`.** `teardown()` returns `void` (`cell.ts:223`), so it cannot feed `failedSteps`. The sequencer calls `provider.revoke`, `provider.quarantine` and `provider.delete` itself, in the adapter's order, and records each outcome. A 404 is done (the adapter already maps it). The readback is `listByTags({automata: "cell", stepKey, attempt: String(attempt), deployment})`, one page. **Any entry means survivor.** Each survivor gets the same three steps once more, then one last readback. A failed step stays in `failedSteps` even if the readback ends up empty: AC-4 says "fails any step".
6. **The lease rule turns on in this PR,** with `CELL_RECONCILE_STALE_MS = CELL_LEASE_STALE_MS` (5 min, AC-14's figure).
   - **Margins:**
     - polls every 7 s, which is about 43 polls per window;
     - the setup heartbeat every 60 s, so 5 missed beats are tolerated;
     - the poll loop already fails the run after 3 bad reads (`www-client.ts:46`), so a worker that cannot reach www stops being the cell's owner long before 5 min.
   - **Guard:** a marked run refuses with `cell_poll_interval_too_long` when `pollIntervalMs > CELL_LEASE_STALE_MS / 4` (75 s).
   - **Order: www first, then the worker.**
     - www (`lease: "superseded"`, Decision 12, and the stale rule on) is safe alone: no cell exists until a PR-E worker runs one.
     - A PR-E worker against a www without `superseded` would read a real fence as `refused` and fail loudly. On the supported one-box topology attempts never overlap (Decision 14), so this is a loud failure, not a wrong one. It is still avoided by the order.
7. **The setup heartbeat** is a `thread-status` read with `cellAttempt`, every `CELL_SETUP_STAMP_MS = 60 s` (owned by `cell-run.ts`), from the plan's 200 until the poll loop starts. It never overlaps itself: a beat that is still in flight skips the next tick. Each answer is handled as follows:
   - **`terminal: true`** (a `lease: "finished"` answer): the step is finished and the token is retired. Setup aborts (an internal `AbortController`), `retiredRuns.add(runId)` runs, and the executor returns `{outcome: "completed", finalStatus}` through the normal teardown (E12).
   - **`status: "stopping"`** (a user Stop): setup aborts, and the executor returns `{outcome: "stopped"}`. `runAgentResolved` then posts the `user-cancelled` terminal, as for a box run (E11). Nothing is sent to the daemon.
   - **`lease: "superseded"`** (one read is enough: it is a database fact, Decision 12): setup aborts, and the run takes the **fenced** path. That is own-cell teardown with the vault revoke first, no terminal post, and `{outcome: "fenced"}` (E13).
   - **`lease: "refused"`** on two reads in a row, counting heartbeat and poll reads together, **with no newer attempt** (revoked, done, or no lease, e.g. the reconciler's stale-lease revoke `cell-control.ts:136-138`, live now that this PR turns the stale rule on): setup aborts, and the run **fails loudly** with `cell_attempt_revoked`. The abnormal end posts `daemon-failed`, and the full R → T → B → A → P teardown runs (E13b). The thread therefore ends now, instead of hanging until the stalled-thread watchdog. A single `refused` followed by `renewed` resets the count.
   - **`lease: "error"`:** logged and ignored. The lease ages, and nothing fails.
   - **A 409 `cell_step_conflict`, or a 500 `cell_finish_failed` / `cell_retire_failed`:** these are served only on a terminal read (`thread-status/route.ts:186-241`), so the heartbeat handles them **exactly as the poll does** (Contract 5, E16):
     - the 500s go through the same `cellTerminalRetry` budget (6 tries, 5 s apart) and the same retired-token confirmation (Decision 11);
     - the 409 aborts setup at once and ends as E16-409 (no www teardown calls).
   - **Any other 5xx, a transport error, a timeout (10 s per beat) or a 401/403:** the beat is logged as `cell.heartbeat_failed {status}` and is **not** retried inside the tick. Three failed beats in a row (about 3 min, under the 5-min stale window) fail the run `cell_heartbeat_lost`. A 401/403 counts the same way, which is the confirm rule of `www-client.ts:46`, spread over ticks. The setup step in flight is aborted, and the run tears down. Any success resets the count.
   - **Cancellation:** the heartbeat stops at once when the run signal aborts, or when the poll loop takes over. The poll loop's own reads carry `cellAttempt` from then on.
8. **A refused plan fails the step with its code** (AC-2). `CellPlanRefusedError(code, status)`, owned by `cell-www-client.ts` (phase 4):
   - It is a `NonRetryableError`, whose message is `cell plan refused: <code> (HTTP <status>)`. The code comes from the response `error` field, validated against `^[a-z_]{1,40}$`, else `unknown`. Nothing else from the body is read or logged.
   - The provider factory is never called.
   - The run's existing outer catch claims and posts the abnormal end, as for any pre-daemon throw (`workflow.ts:740-752`).
   - `cells_disabled` (the flag turned off between dispatch and run) is refused like any other, never a silent fallback to the box.
9. **Timeout salvage is not done for cells** in this PR. A timed-out cell's unpushed work is lost, and the typed `timeout` terminal still posts. This is recorded in the risks.
10. **The cell's self-check posts one egress row.** On a successful create, the worker posts one `{destinationHost: "example.org", destinationPort: 443, action: "deny", policyLevel: "domain", mode: "enforce", source: "worker"}` through `postEgressEvents`. That is the measured block of the self-check, and it is what the UAT's "one `deny` row for example.org" expects. **No other code path posts a cell's egress decisions today.** It is best effort and never fails the run.

11. **A `cell_retire_failed` whose retire committed.** If the retire `UPDATE` committed but its response failed, the retry's `thread-status` read gets **401**, because a retired token is refused there (`spec-d.md:56-60`). The rule:
    - After a 500 `cell_retire_failed` (poll or heartbeat), a 401 on a retry is **confirmed** by one `cell-teardown` `revoke` call for this attempt. That route accepts a retired token (`cell-teardown/route.ts:87-92`), and `revokeAttempt` is a no-op after `finishStep`.
    - **The revoke authenticates (200):** the token is retired, so the step is finished. `retiredRuns.add(runId)` runs, the poll returns `{outcome: "completed"}`, and the run tears down as E6. The revoke call counts as R.
    - **The revoke also 401s:** the token is really gone. The run fails `cell_terminal_unconfirmed`.
    - **The confirming call fails** (a 5xx, a transport error or a timeout): retry up to 3 times with backoff (1 s, 2 s, 4 s), each under its own 10 s timeout. Still unconfirmed: fail the run **loudly** with `cell_terminal_unconfirmed`, with the typed abnormal end and an `error` log line naming the attempt.
    - It applies only after a `cell_retire_failed`. Any other 401 keeps today's confirm-then-fail rule.
12. **Only `lease: "superseded"` means fenced. A fenced attempt never posts a terminal, and never fails.**
    - **The signal must be authoritative,** so www provides it. PR-E adds it to `thread-status` (phase 7).
      - Where `stampSeen` runs (`cell-authority.ts:350-377`), a refused stamp is classified with one read of `cell_step` by key: `current_attempt > attempt` → `"superseded"`; anything else (revoked through this attempt, done, no lease, unknown step) → `"refused"`.
      - **Order:** the classifier runs **only after `stampSeen` returns `false`**, so a renewed poll costs no extra read. If the classifier throws, the answer is `lease: "error"` (logged, 200, status still served), the same as a `stampSeen` throw. The worker ignores `error`, so a classifier outage can neither fence nor fail a run.
      - `stampSeen`'s boolean contract is kept for its callers. The classifier is a new `leaseRefusal({db, stepKey, attempt})`, or `stampSeen` gains a typed result. The implementer picks the smaller diff, and the www tests pin the mapping.
      - `thread-status`'s `lease` union gains `"superseded"`.
    - **Nothing else is a fence signal.** The worker never infers a fence from `revoked: false` on `cell-teardown`, from a 401, or from any code a route does not return.
      - `cell-plan`'s `409 superseded` is a **different** thing: a newer open of the same `requestId` (H2). It is retried with the same id, and it never reaches this path.
      - `refused` with no newer attempt is a revocation, handled loudly as `cell_attempt_revoked` (Decision 7, E13b).
    - **Why no terminal:** a redelivered run keeps the **same** `runExternalId` (the workflow run id, `workflow.ts:518-531`), and the run-terminal fence refuses only a **different** generation (`apps/www/src/app/api/daemon/run-terminal/route.ts:55-95`). So a `daemon-failed` terminal from the fenced old run would pass the fence and `markThreadTerminal` the thread that the new attempt is running. onFailure's `run-failed` post would do the same.
    - **Rule:** on `superseded` the executor:
      1. **first** calls `provider.revoke` (the vault) on its own `cellId`, before it stops anything or makes any www call. That shuts the window in which its daemon can still post `daemon-event`s (Risk R9);
      2. sets `abnormal.claimed = true` with no end, so the outer catch posts nothing;
      3. then runs R for its own attempt (a no-op in substance: `openNextAttempt` already fenced attempt _n_'s bearer), `quarantine` and `delete` on its own `cellId`, B tagged with its own attempt, and P for its own attempt, with **no A**;
      4. **returns** `{outcome: "fenced"}`, a new `AgentRunOutput` outcome (`types.ts:301-313`), instead of throwing. The engine records COMPLETED, so onFailure never runs, and `runAgentResolved` posts nothing for `fenced`.
    - **AC-3's order on this path:** the vault revoke runs before the www revoke here. AC-3's purpose, a dead broker bearer before the local teardown, already holds, because the fence revoked attempt _n_ server-side when _n+1_ opened. This is a deliberate, recorded deviation for the fenced path only. Every other exit keeps R first.
    - It never reads or writes the newer attempt: every call carries its own attempt number.
13. **Before `create`, a newer attempt removes its predecessors' cells on the same server** (the cell twin of the box removing a prior container by name, `workflow.ts:1300-1303`):
    - After the plan's 200 and before `create`, the executor calls `listByTags({automata: "cell", stepKey, deployment})` (one page) on **this box's** server.
    - Every entry whose `Number(tags.attempt) < attempt` gets the step-by-step teardown: `provider.revoke` (vault) → `quarantine` → `delete`.
    - **The order differs from "quarantine, then tear down":** OpenSandbox 1.2.1 refuses a deny-all while the vault still holds a binding (`gate-log-g.md:77`), so the vault revoke must come first.
    - Entries with an equal or higher attempt are never touched.
    - **Failures:** a list or step failure is logged (`cell.prior_reap_failed {stepKey, attempt: <old>}`) and does not block the create. The predecessor's attempt is already fenced in www, and the reconciler reaps it.
    - **When it fires:** a worker crash (E14) redelivered to the **same** box. On one box, the old run is dead when the new one starts.
14. **Supported topology: one box per deployment.**
    - **On one box, attempts of one run never overlap:**
      - systemd stops the old worker before it starts the new one. `ExecStop` drains up to 1800 s, `KillMode=mixed` and `TimeoutStopSec=2100` (`automata-worker.service:85`, `:98`, `:104`);
      - a redelivery that lands while the same run id is still in flight in-process waits for it (`guardRunTerminal`, `run-terminal-ledger.ts:220-236`), and then is refused (E15).
    - **Across two boxes** attempts _n_ and _n+1_ can overlap. The new box's `listByTags` asks only its own server, so it cannot see cell _n_, and www's reconciler reaches only the server behind its one tunnel hostname. That case is covered **only** by the fence (Decision 12, through `superseded`) and by the expiry backstop (`CELL_RUN_TTL_MS`). It is not a supported topology for cells. The README says so (phase 8).

**Failure inside the finally:**

- **R fails** after 3 tries (5xx, transport, 401/403 confirmed): add `revoke_attempt` to `failedSteps` and **carry on with T**. T is never skipped.
- **A T step fails:** add `vault`, `quarantine` or `delete`.
- **B fails** (list error): add `survivor`. An unreadable state counts as not clean.
- **Deadline hit:** the remaining steps are recorded as failed, B is skipped and counted as `survivor`, and P is still sent with a 5 s budget.
- **P fails** (network or 5xx after 2 tries): log the same `cell_teardown_incomplete` line locally (step key, attempt, steps), and rely on the reconciler. It never throws.

**Idempotency:** R twice → 200 both times (`revokeAttempt` is capped and repeatable). P twice → the second 200 or 401 (token deleted) → `already_reported`. A T step on a gone cell → 404 → done.

### 2. NEW `packages/worker/src/agent-run/cell-config.ts`

	| { kind: "off" }

	env: NodeJS.ProcessEnv,

- **`off`:** none of `WORKER_OPENSANDBOX_URL`, `WORKER_OPENSANDBOX_API_KEY_FILE` and `WORKER_OPENSANDBOX_GUEST_IMAGE` is set.

### 9. `packages/types/src/cell.ts`, `packages/sandbox/src/providers/opensandbox-cell.ts`

- `ICellProvider.copyIn(cellId, path, bytes, opts: {mode: number; owner: string; group: string})`. `CellProviderErrorCode` is unchanged (`http_error`, `invalid_argv`).
- **Wire format** (upstream execd `release-1.2.1`):
  - `parseUploadForm` reads **both** parts from `form.File`, so `metadata` is a **file** part (`filesystem_upload.go:76-90`). Its content is the JSON of `FileMetadata {path, owner, group, mode}`, where `Permission` is embedded and its fields are promoted flat (`model/filesystem.go:28-37`).
  - Upstream reads `mode` as a JSON **int whose decimal digits are parsed as octal**: `strconv.ParseUint(strconv.Itoa(mode), 8, 32)` (`controller/utils.go:66-67`). So 0600 is sent as **`600`**, never `384`. The adapter takes the mode as an octal-digit integer (`600`, `644`, `755`) and refuses any value with a digit above 7 before any HTTP call.
  - **Body:** `FormData` with `metadata` = `Blob([JSON.stringify({path, owner, group, mode})], {type: "application/json"})`, filename `metadata.json`, and `file` = `Blob([bytes])`, filename = the basename. One pair per call.
  - **Owner and group:** the image user, `agent:agent`. The batteries image creates `agent` with uid 10001 (`deploy/images/batteries/Dockerfile:96`, `:179-180`). They are sent explicitly, so the file never depends on execd's process identity.
- **Adapter checks:** the path is absolute and has no `..`, the size is ≤ 16 MiB, the mode is octal digits ≤ `777`, and owner and group match `^[a-z_][a-z0-9_-]{0,31}$`. All of them are checked before any HTTP call.
- **The request:** `retry: "undelivered"`. A non-2xx is `http_error`, and neither the body nor the multipart content is logged.
- **Execd's own log** records `http: POST /files/upload` and the URL only (`router.go:289-293`). The path and the bytes are in the body, so they never reach that log.
- **The only other implementers:** the reconciler and `cell-control.ts` take `Pick<…>` (`reconcile.ts:26`, `cell-control.ts:129`), so they are unaffected. `cellProvider()` returns the full adapter.

## Risks and rollback

- **R1, box-path regression from the admission extraction.** Mitigations: a move with explicit state ownership and re-exports (Decision 2), the existing unit suites and the HATCHET_IT admission and burst drills. The diff of `runAgentInner` is reviewed as a pure move.
- **R2, the dependency closure.** `@terragon/sandbox` pulls the E2B and Daytona SDKs into the worker's install, and CI's `worker-e2e` installs `@terragon/worker...` (`.github/workflows/ci.yml:228`). Only the subpath is imported (T-IMPORT). Check the install time and `pnpm audit`. If it is too heavy, the fallback is to move `opensandbox-cell.ts` to a leaf package, as a follow-up.
- **R3, Claude through `cell-entry.sh` and the daemon** (the one check left after the pre-flight, see "Live pre-flight evidence"):
  - The probe gave Claude its placeholder in `CLAUDE_CODE_OAUTH_TOKEN` on the command line. In a cell, the entry refuses credential-shaped env names and starts the daemon under `env -i` with an allowlist (`cell-image.ts:45-46`, `:93-101`), and the daemon's Claude adapter sets no token env when `useCredits` is false (`claude-adapter.ts:64-77`).
  - **Plan:** the placeholder reaches Claude through the HOME login file written by `copyIn`.
  - **Gate:** the UAT's "Claude Code answers `ok` through the vault", run through `cell-entry.sh` and a daemon message.
  - **If it fails,** the follow-up is a daemon-side placeholder env for cells, never a real token in the guest.
- **R4, the prompt in the guest.** The prompt is written to a 0600 file and removed after the write. It is visible to the agent uid by design (it is the agent's input), and it stays out of execd's command log (Decision 3).
- **R5, no timeout salvage and no OOM signal for cells** (Decisions 7 and 9). A timed-out cell loses unpushed work, and an OOM inside the cell surfaces only as `agentFailure`.
- **R6, the lease rule on** could reap a live cell if a worker stalls for more than 5 min while still believing it owns the cell. That worker's poll loop would already have failed after 3 bad reads. The reap only hits fenced, done or unseen attempts.
- **R7, rollout coupling.** The marker follows the www flag, not the worker's box. A flagged user whose task run lands on a box without OpenSandbox fails `cells_unconfigured` on every run. Turn the flag on only for users whose org runs on a box with the server installed. This is a runbook line in `packages/worker/deploy/README.md`.
- **R8, the retire activates with PR-E.** The first cell run is the first retired token. PR-D's matrix covers it (`retired-daemon-token.integration.test.ts`).
- **R9, the fenced run's daemon window** (cross-box only, Decision 14):
  - **The window:** from the moment _n+1_ opens until fenced run _n_ revokes its own vault, cell _n_'s daemon can still post `daemon-event`s with the shared run token. The vault swaps the real token in on `/api/daemon-event`, and the daemon-event generation fence cannot tell two attempts of the same run apart (same `runExternalId`, `handle-daemon-event.ts:123-141`).
  - **How long:** at most one poll interval to observe `superseded` (7 s), plus one vault-revoke round trip. It is seconds long, because the vault revoke is the fenced path's first action (Decision 12).
  - **What it does not cover:** a fenced run that is itself dead (killed) never revokes. Its cell keeps posting until the TTL backstop expires it, because www's reconciler cannot reach a second box's server.
  - That is the reason one box per deployment is the only supported topology.
- **Rollback:**
  - turn the `opensandboxCells` flag off: no marker, so every run takes the box path, byte for byte (T-FLAG-OFF);
  - or remove `WORKER_OPENSANDBOX_*`: marked runs fail closed, never silently run on the box;
  - reverting the PR restores `CELL_RECONCILE_STALE_MS = null`. The reconciler keeps reaping expired cells.

- **"Turn the lease rule on only together with stamping" (in one deploy):** www and the worker deploy separately. Since no cell can exist before a PR-E worker, either order is safe (Decision 6).
