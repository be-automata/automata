Context frame

Use case. An agent run on the execution box (uid 999 or 2001, inside the worker's cgroup) must be unable to open TCP connections to host-local services it does not own (Hatchet engine gRPC :7077 and API :8888 via docker-proxy and on the Docker bridge, cloudflared :20241, sshd via the box's own public IP or ::1), while its own loopback traffic (the run's egress proxy and git broker, its own test servers, DNS to systemd-resolved, the test Postgres on :25432) keeps working. Decided by who owns the listening socket (cgroup), not by a port list.

Reproduction path. nft-verify.sh creates system.slice/automata-worker.service/verify-probe, moves a shell into it, drops to each slot account, starts listeners after the move, and connects to every row of the target table with a 1 s timeout, reading the rule counters before and after each row. Sources: issue #367 target table and acceptance criteria 1–11; PR #383 and #388 bodies; AGENT-UID-PROVISIONING.md §7.

Prior UAT. none in docs/uat for this area (first run).

Findings

  • info Agent runs poll localhost:8888 (the engine API) and are refused
    A task run under enforce polled 127.0.0.1:8888 and [::1]:8888 every ~10 s (temporary diag log, enforce-diag-sample). This is a refused row of the target table; the run kept working. Likely a repo test harness readiness loop aimed at a hatchet-lite that is not there.
  • info Three egress-proxy unit tests fail inside a task run
    Under the run's NODE_USE_ENV_PROXY the proxy test client goes through the run proxy; the agent re-ran with it unset: 114/114. Not a fence effect (PR #392).
  • low Shared policy validator accepts private-range allowlist entries the box proxy always refuses
    Documented gap in docs/egress-enforcement.md (roborev round 3).
  • info Counters reset on every table (re)load
    The loopback-table counters are since the last load; a by-hand loader run resets them. Read deny counts with that in mind; the verifier prints its own probe windows.
