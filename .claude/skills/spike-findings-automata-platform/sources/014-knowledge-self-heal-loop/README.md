# Spike 014: Knowledge self-heal loop on real merges

## What This Validates
Automata already has a post-merge lane: the `github-pr-merged` intent, the YouTrack ticket audit (ADR-008), and the self-heal tables. This spike tests whether the same lane can keep *company knowledge* true:
- Every merge triggers a claim reconciliation (spike 010's engine).
- Only the claims the merge actually invalidated produce work.
- Each item lands in a human approval queue carrying its provenance: commit, PR, evidence and confidence.

The test is not on fixtures. It replays **5 real merges** of Automata's own `deploy/PILOT-RUNBOOK.md` (1156 → 1514 lines). **`git diff -U0` serves as the oracle.**

## Research
- OpenWiki keeps code docs current with a cron CI job that opens a docs-only PR (`peter-evans/create-pull-request`). That ties the loop to GitHub PRs and Actions.
- qm holds drafts for human review in a durable ledger instead.
- **Chosen:** trigger on merge, use the claims engine (no model call for unaffected claims), and put a queue *outside GitHub*: a page plus exported decisions. Marketing and support approvers don't live in PRs.

## How to Run
```bash
cd .planning/spikes/014-knowledge-self-heal-loop
node --experimental-strip-types --no-warnings run.ts   # PASS/FAIL against the git-diff oracle; writes queue.html
open queue.html
```

## What to Expect
- Five merge lines, each with `FP=0 FN=0`, then `PASS`.
- `queue.html` shows 3 items needing a decision, each with merge sha, PR number, before/after text, evidence and re-anchor confidence. It has Approve and Reject buttons and an exported decisions JSON.

## Observability
`events.jsonl` has one event per merge: flagged, oracle, FP, FN, model calls, op ids and post-approval drift. `results.json` holds every op.

## Investigation Trail
1. **Seeding.** 166 paragraph-level claims were generated from the runbook at `75f6af8`, one per paragraph or code block with ≥ 4 tokens. Each statement is the paragraph's first sentence.
2. **First run: the oracle said 0 everywhere.** That's impossible for #287, which is an in-place label rename. Root cause: this machine's git config forces color, so the `@@` hunk headers carried ANSI escapes and the parse regex matched nothing. It was fixed with `--no-color`.
   - **This is a production pitfall:** every git-output parser in the worker must pass `--no-color` (and ideally `-c color.ui=never`).
3. **Second run: one "false positive" (p153, at #306).** That merge added a *second, byte-identical* "Rollout (operator, in this order; …)" line. The relocation index found 2 matching spans and refused to guess (`ambiguous`), which is correct behavior. The scoring was changed to report `ambiguous` separately instead of counting it as a false positive.
4. **A bad update was caught.** Claim p028's statement had come out as `"3."`, because the sentence splitter cut at a list marker. Its re-anchor matched with **score 0**, and the "model" proposed rewriting it to the page *title*. Two fixes:
   - Strip list markers before splitting sentences.
   - Add a **confidence floor** (Jaccard 0.5): anything below it becomes a `review` op ("a human must locate this fact") instead of an `update`.

   After the fixes, p028 is a real catch. Merge #306 changed "As the org owner, open the repository environment…" into "As an org owner or admin, with the org active, open Environment…", and the update was proposed with confidence 0.56.
5. **Granularity limit.** At #287, claim p157's evidence changed (`needs-human` → `needs-human-review`), but its first-sentence statement ("Labels (created on first use by the writer):") never mentioned the label. So the proposed "update" leaves the FAQ text unchanged and re-verifies it. That isn't wrong, but paragraph claims are too coarse: the real build needs **atomic claims**, one fact per claim as OpenWiki does, generated by the model at seed time.

## Results
**VALIDATED.** Across 166 claims and 5 real merges, flags match the git-diff oracle on every merge (**0 FP, 0 FN**, 1 correctly refused ambiguity), and **drift is 0 after approval**.

| Merge | Lines Δ | Flagged | Oracle | Auto repins | For approval | Model calls |
|---|---|---|---|---|---|---|
| #259 self-heal fix loop | +189 | 0 | 0 | 0 | 0 | 0 |
| #272 benchmark harness | +141 | 0 | 0 | 0 | 0 | 0 |
| #287 label rename | in place | 1 | 1 | 0 | 1 | 1 |
| #304 task-run home move | 0 | 0 | 0 | 0 | 0 | 0 |
| #306 org env vars | +28 | 2 | 1 | 137 | 2 | 1 |

- A **+360-line** doc evolution cost **2 model calls** and **3 human decisions**. The 137 content-identical repins applied silently.
- Appends at the end of the file (#259, #272) cost nothing. An insertion mid-file (#306) moved 137 claims, all of them relocated by hash with no model call.

**Signal for the build:**
- **Trigger:** the existing `github-pr-merged` mirror-intake intent, plus ticket-closed and doc-edited webhooks (spike 010's `ticket://` and `doc://` resolvers). One reconcile job per affected page, with zero model calls when nothing intersects.
- **Queue:** a first-class surface outside GitHub (dashboard plus Slack DM to the source owner). Every item carries merge sha, PR, evidence URIs and confidence. Decisions are stored like `auditEffects` so the loop is auditable. Conflicts (spike 010) route to *the owner of the stale source*.
- **Invariants:**
  - Only content-identical repins auto-apply.
  - Updates below the confidence floor become reviews.
  - Ambiguous spans never auto-resolve.
  - Git parsing always uses `--no-color`.
